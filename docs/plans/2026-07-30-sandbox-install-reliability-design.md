# VoIPBin Sandbox — Install Reliability Fix (Call-Manager / Transcribe-Manager Crash Loops, Version Pin Refresh, Env Template Sync)

Status: DRAFT (Design Review Round 0)
Author: Hermes (CPO) with pchero (CEO/CTO)
Date: 2026-07-30
Repo: sandbox

## 0. Mandate

A customer reported that installing VoIPBin via the sandbox failed. We did not have their
logs. This document scopes and designs the fix based on a fresh-install reproduction run
against the current `main` branch (unmodified `versions.lock`), performed in this cycle.

Goal: after this cycle, a fresh sandbox install reaches a stable, fully-running state
(no crash-looping containers) for a new self-hoster, and the version/credential
bookkeeping that made this hard to diagnose is cleaned up so the next drift is easier to
catch.

## 1. Reproduction findings (verified facts)

Full clean-room reproduction was run in this cycle: infra (db/redis/rabbitmq) up →
containerized alembic migration against the pinned Feb-21 dbscheme commit → full 44-service
`docker compose up -d` → `setup_test_customer.sh` against `https://localhost:8443`. Sudo-gated
steps (mkcert CA install, DNS forwarding, VoIP macvlan network setup) could not be exercised
in that session and are explicitly deferred (§5).

**Result: 40/44 containers healthy, 3 crash-looping.**

| Container | Cause | Verdict |
|---|---|---|
| `voipbin-call-mgr` | Unconditionally subscribes to the `bin-manager.sentinel-manager.event` RabbitMQ exchange at startup (`bin-call-manager/cmd/call-manager/main.go`); treats subscribe failure as fatal (`CRITICAL`, process exit). Sandbox's `docker-compose.yml` deliberately omits `sentinel-manager` (requires the Kubernetes API, crash-loops in Compose per its own inline comment), so the exchange is never declared and call-manager can never start cleanly in **any** Compose-based (non-K8s) deployment. | **Fatal, highest priority** — call-manager is core to all call handling. Most likely cause of the customer's reported failure. |
| `sandbox-transcribe-manager-1` | The dummy GCP credentials JSON generated by `init.sh`/`init_no_sudo.sh` is not a parseable private key. transcribe-manager treats "no STT provider available" as fatal and exits, unlike `asterisk-call-proxy`, which logs the same class of init failure and keeps running. | **Fatal, second priority** — inconsistent error-handling vs. the rest of the stack. |
| `voipbin-kamailio`, `voipbin-dns` | Expected: both require the sudo-gated macvlan/DNS setup that was not run in this session. Not new findings, not in scope here. | Not a bug — deferred to §5. |

**Version drift is not implicated.** `versions.lock` pins the Feb-21 monorepo commit while
monorepo HEAD is now Jul-30 (~5 months). Migrations against the Feb-21 pin completed with
zero errors, and both fatal bugs above were confirmed to exist unchanged at current monorepo
HEAD (`a0438c1f2`). Bumping the pin alone would not have fixed the customer's install.

**Env var audit**: no genuinely required variable was found missing or broken. `.env.template`
(58 vars) is out of sync with what `init.sh` actually generates in both directions (some
generated vars undocumented, e.g. `BASE_HOSTNAME`/`API_URL`/`WEBSOCKET_URL`; some documented
vars never written by init, e.g. `DB_HOST`/`REDIS_HOST`, though compose's `${VAR:-default}`
fallbacks mask this in practice). Cosmetic, but real drift.

The customer/agent bootstrap flow fixed in PR #7 (da0c1cd) — customer create → agent password
set → JWT login → billing plan → extensions — was re-verified working with **no regression**.

## 2. Scope

1. **monorepo `bin-call-manager`**: make the sentinel-manager subscribe failure non-fatal
   (log + continue) instead of exiting the process. Affects every non-Kubernetes deployment
   of call-manager, not just this sandbox.
2. **monorepo `bin-transcribe-manager`**: make missing/unparseable STT provider credentials
   disable STT functionality and continue running, matching the existing
   `asterisk-call-proxy` degrade-gracefully pattern.
3. **sandbox `versions.lock` refresh**: regenerate against current monorepo HEAD
   (`a0438c1f2`, 2026-07-30), replacing the Feb-21 ancestry pin. Formalize the resolution
   process (target-commit → per-service latest built tag ≤ target → digest) as a checked-in,
   reusable script rather than the ad-hoc process used for the original pin (da0c1cd), so
   future version bumps don't require this same archaeology.
4. **sandbox `.env.template`**: sync bidirectionally with what `init.sh` actually generates.

## 3. Verification plan

**In this cycle (no sudo required, repeatable):**
- After (1)+(2): rerun the same clean-room procedure used for reproduction (infra up → DB
  migration → full `docker compose up -d` → `docker compose ps`) and confirm zero
  crash-looping containers (previously 3/44).
- After (3): confirm the refreshed pin still migrates cleanly and images pull successfully
  in the same clean-room procedure.
- After (4): rerun `setup_test_customer.sh` and confirm no regression in the customer/agent
  bootstrap flow.

**Deferred to the end of this cycle (requires sudo, requires pchero):**
- Full `sudo ./scripts/start.sh` (mkcert CA, DNS forwarding, VoIP macvlan network).
- Real SIP registration / call flow (`softphone.py`, `test_call.py`).
- Browser-based admin/talk/meet UI check.

## 4. Non-goals

- Not implementing `sentinel-manager` itself in sandbox — it remains an intentional,
  documented Kubernetes-only exclusion.
- Not touching secrets storage — plaintext `.env` stays as-is (decided this cycle: the
  meaningful risk is backup-archive exposure, which is out of scope here and can be
  revisited separately if pursued at all).
- Track A (horizontal-scale enablement) is already complete and out of scope.
- Not a general Track B (install-parity hardening: TLS lifecycle, scheduled backup,
  monitoring stack, public DNS) — that remains a separate, not-yet-started body of work.

## 5. Risks

- (1) and (2) are monorepo core-service changes, not sandbox-only — they need their own
  monorepo PR review loop (CLAUDE.md review-loop policy: minimum 3 code-review rounds,
  until 2 consecutive approvals), separate from this sandbox-repo design/plan.
- (3) risk: some of the 39 images may not have a registry tag at exactly the target
  ancestry commit. Fallback: use that service's nearest earlier tag and document the
  exception explicitly in the generated `versions.lock`, same pattern as the original pin.
- Sudo-gated verification (§3, deferred) is the only path that actually exercises real SIP
  call flow end-to-end; until it runs, "fixed" only means "no crash loops observed", not
  "verified working for real calls". This gap is explicit, not hidden.

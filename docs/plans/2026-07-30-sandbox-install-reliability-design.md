# VoIPBin Sandbox — Install Reliability Fix (Call-Manager / Transcribe-Manager Crash Loops, Version Pin Refresh, Env Template Sync)

Status: DRAFT (Design Review Round 2, addressing Round 1 REQUEST_CHANGES)
Author: Hermes (CPO) with pchero (CEO/CTO)
Date: 2026-07-30
Repo: sandbox (fixes 2.1/2.2 land in monorepo; this doc is the sandbox-side design of record for the whole effort)

## 0. Mandate

A customer reported that installing VoIPBin via the sandbox failed. We do not have their
logs. **This document treats "call-manager's sentinel-manager crash loop is the customer's
failure" as a hypothesis, not a confirmed diagnosis** — it is the single most severe,
100%-reproducible failure found in a fresh clean-room install, and call-manager is core to
all call handling, so it is the leading candidate. Closing the loop with certainty requires
either the customer's logs or their confirmation after this fix ships; this document does
not claim that confirmation.

Goal: after this cycle, a fresh sandbox install reaches a stable, fully-running state (no
unexplained crash-looping containers) for a new self-hoster, the version/credential
bookkeeping that made this hard to diagnose is cleaned up, and the two monorepo-level bugs
found are fixed in a way that does not silently disable functionality.

## 1. Reproduction findings (verified facts)

Full clean-room reproduction was run in this cycle: infra (db/redis/rabbitmq) up →
containerized alembic migration against the pinned Feb-21 dbscheme commit → full 44-service
`docker compose up -d` → `setup_test_customer.sh` against `https://localhost:8443`. Sudo-gated
steps (mkcert CA install, DNS forwarding, VoIP macvlan network setup) could not be exercised
in that session and are explicitly deferred (§6).

**Result: 40/44 containers healthy, 4 down** — 2 real bugs, 2 expected/sudo-gated (not new
findings). (Round-1 review caught this document previously said "3 crash-looping" while
listing four containers; corrected here — 40 + 4 = 44.)

| Container | Cause | Verdict |
|---|---|---|
| `voipbin-call-mgr` | `bin-call-manager/pkg/subscribehandler/main.go:124-134` (`subscribeHandler.Run()`) loops over 4 targets and calls `QueueSubscribe` for each; `QueueSubscribe` delegates to `QueueBind` (`bin-common-handler/pkg/rabbitmqhandler/main.go:34-35`). The queue construction lists `commonoutline.QueueNameSentinelEvent` alongside asterisk-event-all/customer-event/flow-event (`cmd/call-manager/main.go:180-185`). Sandbox's `docker-compose.yml` deliberately omits the `sentinel-manager` service (requires the Kubernetes API, crash-loops in Compose per its own inline comment), so that exchange is never declared, `QueueBind` returns an AMQP 404, and the wrapped error propagates up through `runSubscribe` → `run` → `runCommand` to a `logrus.Fatalf` exit. This is not specific to sandbox — **any non-Kubernetes Compose-based deployment of call-manager hits this**. | **Fatal, highest priority.** Leading hypothesis for the customer's reported failure (see §0). |
| `sandbox-transcribe-manager-1` | `bin-transcribe-manager/pkg/streaminghandler/main.go:83-113` (`NewStreamingHandler`) already treats GCP/AWS client init failure as non-fatal (`log.Warnf`, continues) — that part already degrades gracefully. The actual fatal is at line 112-115: if **both** providers end up nil, the function returns a bare `nil` interface, and `cmd/transcribe-manager/main.go:144-146` turns that into a returned error which unwinds to the same `logrus.Fatalf` exit path as above. Root cause: `init.sh`/`init_no_sudo.sh` generate a syntactically-present but unparseable dummy GCP private key (see §2.4 for the credential itself), so GCP init fails, and no AWS credentials are configured by default, so both are nil. | **Fatal, second priority.** Inconsistent with the *intent* already expressed in the per-provider warnings — the code clearly meant to support "degrade, don't crash" but stops short of it. |
| `voipbin-kamailio` | Requires the `KAMAILIO_EXTERNAL_IP` macvlan interface, only created by the sudo-gated `setup-voip-network.sh`. Expected, not run this session. | Not a bug, deferred to §6. |
| `voipbin-dns` (CoreDNS) | Requires `config/coredns/Corefile`, only generated by the sudo-gated DNS setup step. Expected, not run this session. | Not a bug, deferred to §6. |

**Version drift is not implicated.** `versions.lock` pins the Feb-21 monorepo commit while
monorepo HEAD is now Jul-30 (~5 months). Migrations against the Feb-21 pin completed with
zero errors, and both fatal bugs above were confirmed to exist unchanged at current monorepo
HEAD (`a0438c1f2`). Bumping the pin alone would not have fixed the customer's install.

**Dummy GCP credential is mounted into 3 services, not just transcribe-manager**
(`docker-compose.yml:529` api-manager, `:989` rag-manager, `:1193` transcribe-manager, all
`${GOOGLE_APPLICATION_CREDENTIALS:-./config/dummy-gcp-credentials.json}`). Confirmed in this
session's reproduction that **api-manager and rag-manager stayed healthy** with the same
unparseable credential — both are lazy-init on that path (only touched when a
GCS/RAG-embedding feature is actually invoked, not at process boot), so they are not in
scope for this cycle. Only transcribe-manager parses it eagerly at startup. Flagging this
explicitly rather than silently dropping it, per Round-1 feedback.

**Env var audit**: no genuinely required variable was found missing or broken. See §2.5 for
the concrete `.env.template` sync plan (Round-1 correctly flagged the original wording as
too vague to implement).

The customer/agent bootstrap flow fixed in PR #7 (da0c1cd) — customer create → agent password
set → JWT login → billing plan → extensions — was re-verified working with **no regression**.

## 2. Scope

### 2.1 monorepo `bin-call-manager` — sentinel-manager subscribe fix

**Rejected approach (Round-1 finding): "log the error and continue" is not sufficient.**
`QueueBind` failure with AMQP 404 closes the underlying channel, and all four subscribe
targets (asterisk-event-all, customer-event, flow-event, sentinel-event) share that one
subscribe queue/channel — so "swallow the sentinel error and move on" most likely leaves
call-manager running but **deaf to all four event types**, including the ARI events it
exists to process. That would pass a naive "no crash loop" check while shipping a
non-functional service, which is worse than the current crash loop (silent vs. loud
failure).

**Chosen approach**: defensively `ExchangeDeclare` the sentinel exchange (idempotent,
matching the same kind/durability the exchange is declared with wherever sentinel-manager
itself declares it — the interface already exposes `ExchangeDeclare(name, kind, durable,
autoDelete, internal, noWait, args)`, `bin-common-handler/pkg/rabbitmqhandler/main.go:49`,
and this exact declare-before-bind pattern is already used by `redeclareAll()`,
`main.go:264-311`, for channel recovery — so it is a proven, idempotent pattern in this
codebase, not a new one) immediately before the subscribe loop in
`pkg/subscribehandler/main.go`. This means: if sentinel-manager is deployed (declares the
same exchange), nothing changes. If it is not deployed (sandbox, or any non-K8s
deployment), call-manager declares the exchange itself, binds to it, and behaves
identically to today except it never receives sentinel events (which is already true today
in every environment without sentinel-manager running — there is no regression in
sentinel-triggered recovery behavior versus today's actual working configuration, only
versus a hypothetical one where sentinel-manager exists but the exchange declare races).

**Acceptance criterion (Round-1 required this explicitly)**: after the fix, call-manager
must still receive and process ARI events end-to-end — verified by confirming an actual
call/ARI event flows through in the clean-room verification (§3), not merely "container
does not restart".

**Doc-sync obligation** (Round-1 flagged monorepo `CLAUDE.md`'s mandatory doc-sync rule):
this touches `pkg/subscribehandler/main.go`, so `bin-call-manager/docs/architecture.md`
(if it documents the subscribe-target list / failure behavior) must be updated in the same
PR.

### 2.2 monorepo `bin-transcribe-manager` — graceful STT-unavailable degradation

**Rejected approach (Round-1 finding): removing the `streamingHandler == nil` check alone
will panic** — the nil interface then flows into `transcribehandler.NewTranscribeHandler`
and `runStreaming(streamingHandler)`, both of which call methods on it.

**Chosen approach**: introduce an explicit "STT disabled" state instead of relying on a nil
interface as a sentinel value:
- `NewStreamingHandler` keeps returning `nil` when no provider is available (unchanged
  signal), but `cmd/transcribe-manager/main.go` changes from treating that as fatal to:
  logging a warning, setting an `sttEnabled = false` flag, skipping `runStreaming` entirely,
  and passing a `nil`-safe (not nil-unsafe) streaming handler into `transcribehandler.NewTranscribeHandler`
  — either a null-object implementation of the `StreamingHandler` interface that returns a
  clear "STT not configured" error for every method, or an explicit nil-guard inside
  `transcribehandler` at each call site that currently assumes non-nil. Exact choice
  (null-object vs. guards) is an implementation-phase decision; both satisfy the constraint
  that no method call on a nil interface occurs.
- **Defined behavior when STT is disabled** (Round-1 required this, previously unstated):
  any transcribe API request that would start real-time streaming STT returns a clear,
  documented error (e.g. `STT_NOT_CONFIGURED`) rather than a silent no-op or a panic.
  Non-streaming transcribe-manager functionality (if any exists independent of the
  streaming handler) is unaffected.

**Doc-sync obligation** (Round-1 flagged this specifically): `bin-transcribe-manager/CLAUDE.md`
currently documents "at least one provider must be configured at startup" as an intentional
invariant. This design **reverses that invariant** — it must be rewritten in the same PR,
along with the failure-mode section of `docs/operations.md`, to describe the new
degrade-instead-of-crash behavior and the `STT_NOT_CONFIGURED` API error.

### 2.3 sandbox `versions.lock` refresh — sequencing (Round-1 required this be resolved)

**The contradiction Round-1 caught**: verifying "call-manager/transcribe-manager no longer
crash" against a `versions.lock` pinned to a commit that predates those fixes is impossible
by construction, since that pin's images do not contain the fix.

**Resolved sequencing**, three explicit phases, run in order:

1. **Phase A (this cycle, first)**: land 2.1 and 2.2 as monorepo PRs, through the standard
   monorepo review loop (CLAUDE.md policy: minimum 3 code-review rounds, until 2 consecutive
   approvals). During this phase, clean-room verification of 2.1/2.2 (§3) runs against
   **locally-built images** (`docker compose build call-manager transcribe-manager` against
   the monorepo branch, overriding the registry-pinned digest for just those two services),
   not against `versions.lock`. This is the only way to verify the fix before it is merged
   and published.
2. **Phase B (after Phase A merges to monorepo main and CI publishes images at that merge
   commit)**: regenerate `versions.lock` targeting that merge commit (or monorepo HEAD at
   that point, whichever is later — operator's call at execution time, default to HEAD
   since pchero already decided 2026-07-30→whatever-HEAD-is-then is in scope, not just the
   two fixed services).
3. **Phase C**: rerun the full clean-room procedure (§3) against the Phase-B `versions.lock`,
   this time using the registry-pinned images like a real customer install would, confirming
   the fix survives the full pin-and-pull path, not just a local build.

**Reusable generator script (Round-1 required concrete spec, previously just "a script")**:
- Path: `scripts/generate-versions-lock.sh`.
- Input: a target monorepo git ref (commit SHA or branch), read from an argument (default:
  monorepo's current `main` HEAD via `git ls-remote`/local checkout).
- Process: for each of the 39 `voipbin/*` images currently tracked in `versions.lock`,
  resolve the nearest registry tag at-or-before the target commit (mirroring how the
  original ancestry pin was built for da0c1cd), pull it, record its resolved sha256 digest
  and source git commit SHA.
- Output: a regenerated `versions.lock` with the same schema as today's (`target_commit`,
  `images`, `image_source_tags`, plus a new `generated_by: scripts/generate-versions-lock.sh`
  field so a hand-edited lock is visually distinguishable from a generated one going
  forward).
- Fallback behavior: if a service has no registry tag at or before the target commit
  (should not happen for a target ≥ existing pin, but guard anyway), keep that service's
  current pinned digest unchanged and print an explicit warning line — never silently pin
  to an unrelated/newer tag.
- Idempotency: running it twice against the same target with no new merges produces a
  byte-identical `versions.lock` (excluding a `generated` timestamp field), so it is safe
  to re-run as a check.
- Out of scope for this cycle: wiring this into CI as an automatic drift-detector (e.g. a
  scheduled job that fails when the pin is >N days stale). Worth doing later; not blocking
  this fix.

### 2.4 sandbox dummy GCP credential — explicit non-goal, not silently dropped

(Round-1 flagged this as silently dropped in the prior draft.) This cycle does **not**
change the dummy credential's shape/validity. The fix in §2.2 makes transcribe-manager
tolerate it (and any other absent/invalid STT credential) without crashing, which is the
actual requirement — a real self-hoster who wants working STT still needs to supply real
credentials via `.env`, same as today. api-manager and rag-manager already tolerate the
dummy credential (§1) and need no change.

### 2.5 sandbox `.env.template` sync — concrete, resolvable spec (Round-1 required this)

Per-variable resolution, both directions:
- **Add to template** (generated by `init.sh` today but undocumented):
  `BASE_HOSTNAME`, `API_URL`, `WEBSOCKET_URL`, `REGISTRAR_URL`, `REGISTRAR_DOMAIN`,
  `CONFERENCE_URL`, `CONFERENCE_DOMAIN` — document with their actual generated defaults
  (from `CLAUDE.md`'s own table, which already has correct values — this is a template
  file gap, not a knowledge gap).
- **Keep in template, annotate as compose-internal-default** (documented today, not
  written by `init.sh`, but consumed via `${VAR:-default}` in `docker-compose.yml` so the
  default already matches): `DB_HOST`, `DB_PORT`, `REDIS_HOST`, `REDIS_PORT`,
  `RABBITMQ_HOST`, `RABBITMQ_PORT`, `KAMAILIO_DB_HOST`, `KAMAILIO_REDIS_HOST`,
  `RTPENGINE_INTERFACE`, `RTPENGINE_PORT_MIN`, `RTPENGINE_PORT_MAX`,
  `RTPENGINE_LISTEN_HTTP`. Add a one-line comment in the template next to each: "compose
  default is used unless you override this — see Track A externalization,
  docs/plans/2026-07-05-...-design.md, for the multi-host case." This directly serves
  §0's goal (the next drift is easier to catch) by making clear which vars are
  init-generated vs. compose-defaulted, instead of the template silently mixing both
  categories with no distinction.
- **Drift check** (Round-1 required a mechanism, not just a one-time sync): add
  `scripts/check-env-template-sync.sh`, run manually for now (CI wiring is out of scope,
  same as §2.3's generator) — greps `init.sh`'s `.env` heredoc/write calls for variable
  names, greps `.env.template` for documented variable names, and prints any variable
  present in one but not the other, exit non-zero if any found (excluding the
  compose-internal-default set above, which is intentionally template-only).

## 3. Verification plan

**Phase A verification (locally-built images, §2.3):**
- Build `call-manager` and `transcribe-manager` from the fix branch, override those two
  services' images in the clean-room `docker compose up -d` run.
- Confirm `voipbin-call-mgr` and `sandbox-transcribe-manager-1` reach a running,
  non-restarting state.
- **Confirm call-manager still processes ARI events** (not just "doesn't crash") — drive a
  test call or synthetic ARI event through and confirm call-manager's logs show it consumed
  from the asterisk-event-all queue, satisfying §2.1's acceptance criterion.
- **Confirm transcribe-manager's disabled-STT behavior is correct**, not just "doesn't
  crash" — issue a transcribe-start API request against it with the dummy credential in
  place and confirm it returns the defined `STT_NOT_CONFIGURED`-class error rather than
  hanging, panicking, or silently no-op'ing.
- Rerun `setup_test_customer.sh`, confirm no regression.

**Phase C verification (registry-pinned images, §2.3, after monorepo merge + versions.lock
refresh):**
- Full clean-room procedure (infra → migration → full `docker compose up -d`) against the
  refreshed `versions.lock`.
- **Pass criterion, corrected per Round-1**: only `voipbin-kamailio` and `voipbin-dns` are
  down, and both are attributable solely to the sudo-gated setup not having run in this
  session (§1) — not "zero containers down", which is unachievable without sudo and would
  be silently reinterpreted during implementation if left as originally worded.
- Confirm image pulls succeed for all 39 pinned images at the new target commit; any
  fallback-pin exceptions (§2.3) are documented in the regenerated `versions.lock` and
  called out explicitly in the PR description, not buried.

## 4. Non-goals

- Not implementing `sentinel-manager` itself in sandbox — it remains an intentional,
  documented Kubernetes-only exclusion.
- Not changing the dummy GCP credential's content/validity (§2.4).
- Not touching secrets storage — plaintext `.env` stays as-is (decided this cycle: the
  meaningful risk is backup-archive exposure, out of scope here).
- Track A (horizontal-scale enablement) is already complete and out of scope.
- Not a general Track B (install-parity hardening: TLS lifecycle, scheduled backup,
  monitoring stack, public DNS) — that remains a separate, not-yet-started body of work.
- Not wiring §2.3's generator or §2.5's drift check into CI as an automated recurring job
  — both ship as manually-invoked scripts this cycle; CI automation is explicitly future
  work, not silently dropped.

## 5. Risks

- **R1 — production behavior regression from making sentinel-subscribe non-fatal (Round-1
  required this be added; previously unstated).** In a real Kubernetes deployment where
  sentinel-manager legitimately should be running, the declare-before-bind fix (§2.1) means
  a genuine sentinel-manager outage or misconfiguration now starts call-manager successfully
  instead of crash-looping loudly — `EventSMPodDeleted`-driven pod-recovery
  (`bin-call-manager/pkg/callhandler/event.go:85`) would silently stop working with no
  crash to signal it. Mitigation to carry into the monorepo PR: emit a periodic metric/warn
  log if the sentinel exchange was self-declared (i.e., sentinel-manager's own declare never
  happened) rather than only logging once at startup, so a K8s operator has an ongoing
  signal, not just a boot-time log line easy to miss. Same shape applies to §2.2 — silently
  degraded STT in a production deployment that expected it to work is worse than a crash if
  there is no ongoing signal; the `STT_NOT_CONFIGURED` API-level error is the primary
  mitigation (a caller finds out immediately when they try to use it), but there is no
  standing "STT is disabled" health/metric signal for an operator who isn't actively calling
  the API. Consider one for the monorepo PR; not blocking sandbox's fix from shipping.
- **R2 — version refresh safety is not the same claim as "drift didn't cause this bug"
  (Round-1 required this distinction).** §1 shows the 5-month drift did not cause the two
  bugs fixed here. It does not show that bumping 39 images across 5 months of monorepo
  history is itself risk-free. Phase C's verification (§3) only checks for crash loops and
  the customer-bootstrap flow; it does not exercise real SIP/call flow (deferred, §6). The
  refresh can plausibly introduce breakage that this verification cannot detect until the
  deferred sudo-gated pass runs.
- **R3 — rollback plan (Round-1 required this, previously absent).** If Phase C's refreshed
  `versions.lock` regresses something: `git revert` the versions.lock commit restores the
  Feb-21 pin immediately (sandbox side, no dependency on anything else). If either monorepo
  fix (2.1/2.2) regresses something post-merge: standard monorepo PR revert; since Phase B's
  `versions.lock` refresh depends on Phase A having merged, reverting a Phase-A monorepo PR
  after Phase B already shipped a lock pointing past it would require re-running Phase B's
  generator against the pre-revert commit as well — call this out explicitly in the Phase-B
  PR description so it isn't a surprise later.
- **R4 — hypothesis, not confirmed diagnosis (Round-1 required toning this down; addressed
  in §0 and inline in §1's table verdict).** We do not have the customer's logs. This fix
  addresses the most severe, 100%-reproducible failure found, which is a strong candidate,
  not a confirmed match to the specific customer report.
